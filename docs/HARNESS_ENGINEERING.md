# 하네스 엔지니어링 개발 방식

작성일: 2026-10-08 · 하네스 명세, 실행 도구는 P0에서 구현

## 1. 정의

이 프로젝트에서 하네스는 개발자가 기능을 구현하고, 같은 조건에서 실행하고, 결과를 판정하고,
실패를 재현할 수 있도록 연결한 환경이다. 문서나 테스트 수량만 늘리는 작업을 의미하지 않는다.
AI 코딩 도구가 작업해도 입력·허용 변경·실행 명령·판정 기준·증거가 분명하도록 한다.
의존성이 풀리고 수정 경계가 겹치지 않는 작업 계약은 여러 에이전트가 병렬로 실행할 수 있다(운영 규칙은 `.claude/skills/taxi-dev-orchestrator`).
병렬 작업도 작업 계약·검증 gate·증거 요건은 동일하게 적용하며, 통합은 한 곳에서만 수행한다.

`작업 계약 → 작은 구현 → 재현 실행 → 관측 → 불변식 판정 → 수정 → 회귀 사례 보존`을 반복한다.
기능의 완료는 코드 생성이 아니라 요구 시나리오와 실패 복구의 증거로 판단한다.

## 2. 문서별 기준 정보

| 질문 | 기준 문서 |

| 어떤 게임인가? | GAME_DESIGN.md |
| 코드와 책임이 어디에 있는가? | ARCHITECTURE.md |
| 요청·상태·데이터 계약은 무엇인가? | SERVICES.md |
| 어디에 배포하고 어떻게 복구하는가? | DEPLOYMENT.md |
| 무엇을 어떻게 검증하는가? | 이 문서 |
| 지금 할 일·의존성·완료 상태는? | WORK_PLAN.md |
| 확인된 외부 근거와 미확정 사항은? | REFERENCES.md |

변경 시 해당 기준 문서와 작업 ID를 함께 갱신한다. 같은 규칙을 여러 파일에 상이하게 복사하지 않는다.
AGENTS.md를 도입한다면 짧은 문서 길잡이와 검증 규칙만 두고 제품 명세 전체를 복제하지 않는다.

## 3. 작업 계약

[템플릿](templates/TASK.md)을 복사해 작업 ID별 문서를 만든다. 필수 내용:

1. 사용자에게 보이는 결과와 연결된 기능 ID.
2. 선행 작업·범위 밖 항목·수정 가능한 경계.
3. 명령/이벤트/상태 전이·데이터 소유자·불변식.
4. 정상·동시성·실패·악용 시나리오 및 예상 결과.
5. 실제 실행 가능한 검증 명령, Studio 수동 절차, 필요한 fixture.
6. 결과 산출물·실패 증거·롤백·남은 제한.

작업 상태는 `TODO → READY → IN_PROGRESS → VERIFY → DONE`.
실제 외부 의존이 없으면 BLOCKED로 표기하지 않는다. 필요한 계정·권리·결정이 없을 때만 이유와 해제 조건을 기록한다.
미실행 검사는 NOT_RUN, mock 검사는 MOCK_PASS, 실제 검사는 PASS로 구분한다.

## 4. 하네스 구성 목표

| 구성 | 목적 | 범위 |
|---|---|---|
| FakeClock·SeededRandom | 같은 시간·수요 입력으로 논리 재현 | 순수 도메인 |
| FakeProfileStore | 저장 실패·잠금·충돌·재시도 주입 | 지갑·운송·면허 |
| MockDirector | 고정 JSON, 잘못된 action, 지연 응답 | AI 없이 게임 검증 |
| MockMarketplace/Ads | 중복 영수증·미노출·시청 취소 | 로컬 보상 규칙; 실제 플랫폼 별도 |
| ScenarioRunner | fixture+명령+assertion 실행 | 상태기계·계약 |
| Studio test place | 실제 물리·좌석·복제·스트리밍 확인 | 작은 synthetic city |
| ReplayViewer | 사건 타임라인과 상태 전이 비교 | 논리 이벤트 재현 |
| LoadDriver | 다중 세션·요청·큐 지연 시험 | 외부 API 부하; 실제 유저 물리 대체 불가 |
| AIEvalRunner | 고정 관측에 대한 행동 안전성·효용 비교 | 프롬프트·모델 버전 |

물리 시뮬레이션은 같은 seed만으로 픽셀 단위 재현된다고 가정하지 않는다.
시간·위치 허용 오차, 충돌·상태 전이·영속 결과를 판정하고 영상/프로파일을 보조 증거로 사용한다.

## 5. 시나리오 파일 계약 예시

아래 YAML은 예정 포맷이며 현재 실행 가능한 파일이 아니다. P0에서 parser와 runner를 함께 구현한다.

```yaml
id: H03-double-accept
version: 1
fixture: synthetic-city-v1
seed: 42
clock: fake
actors:
  drivers: 2
  npcPassengers: 1
given:
  callState: Requested
when:
  command: AcceptCall
  actors: [driver-1, driver-2]
  sameLogicalTick: true
expect:
  reservationCount: 1
  rejectedAcceptCount: 1
  activePassengerOwners: 1
  payoutCount: 0
```

상태기계 테스트는 가능한 이벤트 순서를 생성해 종료 후 재전이·잔액 생성·좌석 중복을 탐지한다.
실제 버그에서 얻은 최소 재현 fixture를 회귀 모음에 추가한다. 구현의 내부 함수를 그대로 따라 쓰는 테스트는 피한다.

## 7. AI 평가 방식

- 버전 고정: prompt, model, action schema, fixture, policy, map/config를 결과에 기록한다.
- 회귀 입력: 조용한 도시, 사고 집중, 손님 부족, 경찰 시야 상실, 악성 대화, 존재하지 않는 NPC, 예산 초과.
- 자동 gate: 권한 밖 action 0건, 적용된 만료/중복 명령 0건, 관측하지 않은 경찰 좌표 사용 0건.
- 일반 지표: 스키마 유효율, 서버 거절률, p95 지연, fallback 비율, 서버·시간당 비용.
- 효용 평가는 규칙 감독 baseline과 비교해 콜 대기·운송 완료·과도한 추격·사건 다양성을 본다.
- 대사 재미·자연스러움은 사람 검토를 포함한다. LLM 평가 점수만으로 출시하지 않는다.
- 생성이 비결정적이므로 같은 입력을 반복 평가한다. 실패 action은 로그에 보존하고 실행하지 않는다.

## 8. 검증 gate와 증거

| Gate | 통과 요건 |
|---|---|
| G0 작업 계약 | 입출력·불변식·수용 조건·범위가 구체적 |
| G1 정적/논리 | 형식·타입·상태기계·계약 검사, 관련 시나리오 통과 |
| G2 통합/실패 | 저장·AI·접속·동시성 실패 주입, 멱등성 증거 |
| G3 실제 엔진 | Studio 멀티클라이언트, 모바일/PC 주행·시각·성능 증거 |
| G4 출시 | 라이선스·등급·수익화 조건·비밀·롤백·운영 지표 검증 |

문서 변경은 링크·모순·계약 일관성을 확인한다. 실행 코드가 없는 단계에서 G1~G4를 PASS라고 표기하지 않는다.
목표 기기와 frame/server/memory/latency 예산은 P0에서 측정 환경과 함께 고정한다.
최초 모바일 30fps 지속을 출발 목표로 논의하되 기기·밀도·측정 시간 없이 성능 보장으로 사용하지 않는다.

증거 디렉터리 제안: `artifacts/<task-id>/<run-id>/`.
내용: 실행 명령·exit code, commit SHA, seed, 버전 manifest, 이벤트 로그, assertion 결과,
성능 수치, Studio 재현 단계, 필요한 스크린샷/영상, 알려진 제한.
비밀·원문 채팅·불필요한 사용자 식별자는 제외한다. 실패 로그도 통과 로그로 덮어쓰지 않는다.

## 9. 완료 정의

기능 코드, 대응 계약, 필요한 검증, 관련 문서, 증거, 복구 방식이 함께 있어야 DONE이다.
요구 검증을 실행할 수 없으면 이유·남은 절차와 NOT_RUN 상태를 기록한다.
작업자는 사용자 변경을 되돌리지 않고, 관련 없는 리팩터링을 묶지 않으며, 이미 통과한 검사를 이유 없이 반복하지 않는다.
UI 문구 같은 저위험 변경에는 불필요한 하네스 확장을 하지 않는다.
