# 택시 개발 오케스트레이터

**실행 모드: 혼합** — 구현은 worktree 서브에이전트 병렬, 검증·피드백은 이름 있는 지속형 에이전트(SendMessage), 통합은 리더(메인)가 단독 수행.

## 0. 상태 파악 (항상 먼저)
1. `docs/WORK_PLAN.md`의 상태와 `docs/tasks/`를 읽는다. `git status`, `git worktree list`로 진행 중 작업을 확인한다.
2. 요청 유형 판단:
   - 새 단계 진행 → 1단계부터.
   - 특정 작업 재실행/수정 → 해당 작업의 TASK 문서와 `artifacts/<ID>/` 최근 실패 증거를 읽고 그 에이전트에만 피드백(2·3단계 부분 실행).
   - 증거가 이미 PASS인 작업은 이유 없이 다시 돌리지 않는다.

## 1. P0 게이트 (병렬 전 직렬)
T001 → T002가 DONE이 아니면 병렬 구현을 시작하지 않는다. 검증 명령이 없으면 병합 시점에 판정이 불가능하다. 이때는 `harness-engineer` 하나만 T001, T002 순서로 실행한다. 이후 T003/T004는 병렬 가능.

## 2. 배치 계산
다음 조건을 모두 만족하는 작업만 같은 라운드에 넣는다.
- 선행(WORK_PLAN)이 DONE.
- TASK 문서(`taxi-task-contract`)가 READY.
- 라운드 내 다른 작업과 **수정 경로가 겹치지 않음**. 공용 파일(`default.project.json`, `src/shared/contracts/**`, `docs/**`)은 어떤 에이전트도 직접 수정하지 않고 리더가 순차 반영.
- 라운드당 동시 에이전트 3~4개 이하(리뷰·병합 부담 때문).

담당 매핑: T001~T004→harness-engineer(T004의 서비스 부분·T003 저장 부분은 backend-engineer), T1xx/T3xx/T5xx/T601→gameplay-engineer, T2xx→world-engineer, T4xx/T602/T7xx/T802→backend-engineer.

## 3. 실행
1. 작업마다 `Agent(subagent_type: <담당>, isolation: "worktree", name: <task-id>, run_in_background: true)`를 **한 메시지에 묶어** 호출한다. 프롬프트에는 TASK 문서 경로, 브랜치명 `<task-id>-<slug>`, 수정 경로, 완료 시 보고할 내용(변경 요약·실행한 명령·증거 경로)을 넣는다.
2. 완료 알림이 오면 `qa-verifier`(이름 지정 지속형)에 `taxi-verify-gate`로 검증을 요청한다. 여러 작업이면 같은 qa-verifier에게 순차 전달한다.
3. FAIL이면 qa-verifier가 담당 에이전트에게 SendMessage로 재현 절차를 전달해 수정시킨다. 같은 원인으로 2회 실패하면 사용자에게 보고한다.

## 4. 통합 (리더 단독)
1. PASS인 브랜치만 `dev`로 병합한다. 병합 순서는 공용 계약 변경이 있는 것 → 없는 것. 충돌이 나면 에이전트에게 돌리지 말고 리더가 해결하되 해결 내용을 기록한다.
2. 병합 후 빌드·린트·테스트 전체를 한 번 실행(회귀 확인).
3. `doc-keeper`로 WORK_PLAN 상태 갱신과 문서 정합성 점검을 한 번에 수행한다.
4. 커밋·푸시·PR은 사용자가 요청할 때만 한다.

## 오류 처리
- 에이전트 실패/무응답: SendMessage로 상태 확인 → 1회 재시도 → 같은 유형을 새 이름으로 재실행하며 맥락을 프롬프트로 전달.
- 한도 소진·권한 거부·도구 설치 불가처럼 재시도해도 같은 실패: 재시도하지 않고 부분 산출물을 직접 확인해 NOT_RUN으로 기록하고 사용자에게 보고(한도는 해제 시각 포함).
- 에이전트가 하지 않은 판단은 추측으로 채우지 않는다.
- 수정 경로 위반을 발견하면 해당 변경을 병합하지 않고 되돌려 재작업시킨다.

## 데이터 전달
- 작업 계약·증거: `docs/tasks/<ID>.md`, `artifacts/<ID>/<run-id>/` (파일).
- 에이전트 간 피드백: SendMessage. 최종 요약: Agent 반환값.

## 테스트 시나리오
- 정상: T001 DONE 후 "T101, T201, T002 병렬로 진행해" → 수정 경로 겹침 검사 → worktree 3개 병렬 실행 → qa-verifier 판정 → PASS 브랜치 병합 → WORK_PLAN 갱신.
- 오류: T101이 `default.project.json`을 수정함 → qa-verifier가 경계 위반 FAIL → 병합 보류, 변경 요청을 리더에게 회부 → 리더가 반영 후 재검증.
- 오류: T002 미완료 상태에서 "T303 해줘" → 1단계 게이트로 거절하고 선행 작업을 제안.
